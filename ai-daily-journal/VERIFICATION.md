# AI日誌 検証記録

## 判定の考え方

この公開版に標準実装は含まれない。そのため「同じコードが全PCで動くか」ではなく、構築を担当するAIが環境差を確認し、同じ受け入れ条件まで到達できるかを検証する。

全体の終了状態は `PASS / PARTIAL / BLOCKED`、個別項目は `PASS / FAIL / 未確認 / 対象外` で記録する。

- `PASS`：成果物または実状態を再読込して確認した
- `PARTIAL`：安全に実装できた範囲はあるが、必須項目に未確認または未対応が残る
- `BLOCKED`：安全、権限、ログ、保存先、意味統合の実行主体などが不足し、主要経路を作れない

## 2026-08-17 v1.0隔離試験

公開commit `b5cc48a` を匿名取得し、本人の実ログ、Obsidian、既存自動化へ触れない試験領域で実行した。

試験条件：

- 新しいCodex実行と新しいClaude Code実行を別々に使用
- Codex／Claude Codeの架空JSONLを各1ファイル使用
- 疑似APIトークンと疑似パスワードを元ログへ混入

確認できたこと：

- 両方のAIが日誌生成まで到達した
- Claude Code側は42項目の受け入れ試験がPASSした
- AI別抽出、統合、必須見出し、疑似秘密情報の除外、同日スキップ、排他制御、7時設定、補完経路を確認した

見つかった問題：

- `AI-Journal` と `ai-journal` がmacOSで同じフォルダとして扱われた
- Claude Codeは試験中に衝突を検出して修正したが、Codex側は衝突を残した
- 両方とも、指定された1ファイルだけを読む実装になり、実環境の複数セッション探索は未対応だった
- 7時の設定内容は確認したが、実際の7時発火は確認していない

この結果を受け、v1.1ではフォルダ衝突の拒否、複数ログ探索、実スキーマ確認、意味統合の実行主体、失敗系試験、公開後監査を必須契約へ追加した。

### 試験中に見つけて修正した機密境界

Codexの初回試験では、スキーマ調査コマンドがraw本文をterminalへ表示した。日誌や保存ログへは残らなかったが、公開条件として不十分だった。

そこで両プロンプトへ次を追加した。

- スキーマ調査で出力できる値を、キー名、型、件数、配列長、timestamp形式、`type`、`role`へ限定
- raw本文を表示してから後で伏せる処理を禁止
- ローカル処理で先に秘密情報と不要な個人情報を除外し、AIはredacted digestだけを読む
- 日誌だけでなく、digest、terminal、通常ログ、エラーログ、テスト失敗出力も秘密値検査の対象にする

修正版をCodexの読み取り専用preflightで再試験し、4ファイル10イベントを集計しながら、terminal出力が許可した構造情報だけであることを確認した。

## v1.1の必須受け入れ条件

| 領域 | 合格に必要な証拠 |
| --- | --- |
| 環境 | OS、タイムゾーン、保存先、ログ取得元、自動実行方法を実物から確認 |
| 取得 | 各AIの実在パス、ファイル数、対象日件数、読めたスキーマを記録 |
| 複数ファイル | 単一固定ファイルではなく、確認した保存構造に沿って対象日分を横断 |
| 安全 | 元ログのハッシュ不変、秘密情報が日誌・digest・terminal・通常／エラーログ・テスト結果へ出ない |
| 品質 | AI別digestから重複を除き、事実・報告・考察を分けて意味を統合 |
| 保存 | 日付lock、一時出力、検証、既存非上書き、原子的公開、公開後監査 |
| 失敗 | 空ファイル、未知スキーマ、同時実行、途中停止、元ログ変化で安全停止 |
| 自動実行 | 毎朝7時、固定日付なし、次回補完、登録内容の再読込、同じ入口の手動試験 |
| 完了報告 | 全項目をPASS／未確認／未対応で分け、証拠パスと残るリスクを記載 |

## 保証しないこと

Codex、Claude Code、OS、ログ形式は更新されるため、将来の全環境での動作は保証しない。

プロンプトを実行したAIが、実環境を確認せず固定パスや推測で実装した場合は不合格。受け入れ表に未確認が残る場合も、利用者は完成したものとして扱わないこと。
